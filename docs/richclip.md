# Proposal: rich Wayland clipboard history manager in Rust

Build a clipboard history system that stores each clipboard selection as a **grouped item** containing all offered MIME representations, plus editable metadata used for search, labelling, thumbnails, and picker display.

The key difference from `cliphist` is:

```text
cliphist entry:
  one blob

new entry:
  stable item id
  many MIME blobs
  metadata
  thumbnail/cache data
  updateable fields
```

Wayland supports this model: a clipboard offer advertises multiple MIME types, and receivers can request specific types over file descriptors; the protocol explicitly allows receive requests for different MIME types. `wl-copy` is not enough for faithful restore because its man page says it currently cannot copy data in multiple MIME types at the same time. ([wayland.freedesktop.org][1]) ([man.archlinux.org][2])

---

## Goals

The system should support:

```text
capture clipboard item
  enumerate MIME types
  read selected MIME types
  group them under one item id

restore item
  advertise all stored MIME types
  lazily serve the requested format

modify item
  add MIME type
  remove MIME type
  replace MIME type
  edit metadata/labels

query item
  list/search history
  inspect formats
  feed picker UI

watch item changes
  let an external labeller react to new entries
  update entries after async processing
```

Target environment: **Sway/wlroots first**, using `wlr-data-control`. The `zwlr_data_control_offer_v1.receive` API is the practical capture path for clipboard-manager-style clients on wlroots compositors. ([wayland.app][3])

---

## Architecture

```text
richclipd
  Wayland data-control client
  captures clipboard offers
  owns/restores clipboard selections
  writes item records and blobs
  emits events over unix socket

richclip
  CLI frontend
  list/update/delete/watch/restore/decode
  talks to daemon over unix socket
  can also read DB directly for simple list/search

store
  sqlite metadata DB
  content-addressed blob directory
  thumbnail/cache directory
```

Suggested paths:

```text
$XDG_RUNTIME_DIR/richclip.sock
$XDG_DATA_HOME/richclip/db.sqlite
$XDG_DATA_HOME/richclip/blobs/aa/bbcc...
$XDG_CACHE_HOME/richclip/thumbs/<item-id>.webp
```

## Data model

Core concept: an `Item` is a grouped clipboard selection. A `Format` is one MIME representation within that item.

```rust
struct Item {
    id: Uuid,
    created_at: OffsetDateTime,
    updated_at: OffsetDateTime,
    source: ItemSource,
    title: Option<String>,
    label: Option<String>,
    search_text: Option<String>,
    item_hash: String,
    deleted_at: Option<OffsetDateTime>,
}

struct Format {
    item_id: Uuid,
    mime: String,
    blob_hash: String,
    size: u64,
    captured_at: OffsetDateTime,
    role: FormatRole,
}

enum FormatRole {
    Offered,      // captured from real clipboard offer
    Derived,      // generated by us, maybe offered on restore
    Internal,     // metadata/cache, never offered on restore
}
```

SQLite shape:

```sql
CREATE TABLE items (
  id TEXT PRIMARY KEY,
  created_at INTEGER NOT NULL,
  updated_at INTEGER NOT NULL,
  source TEXT NOT NULL,
  title TEXT,
  label TEXT,
  search_text TEXT,
  item_hash TEXT NOT NULL,
  deleted_at INTEGER
);

CREATE TABLE formats (
  item_id TEXT NOT NULL,
  mime TEXT NOT NULL,
  blob_hash TEXT NOT NULL,
  size INTEGER NOT NULL,
  captured_at INTEGER NOT NULL,
  role TEXT NOT NULL DEFAULT 'offered',
  offer_on_restore INTEGER NOT NULL DEFAULT 1,
  PRIMARY KEY (item_id, mime),
  FOREIGN KEY (item_id) REFERENCES items(id)
);

CREATE TABLE metadata (
  item_id TEXT NOT NULL,
  key TEXT NOT NULL,
  value_json TEXT NOT NULL,
  PRIMARY KEY (item_id, key),
  FOREIGN KEY (item_id) REFERENCES items(id)
);
```

Content-addressed blobs:

```text
blob_hash = blake3(bytes)
item_hash = blake3(sorted list of (mime, blob_hash))
```

This gives dedupe without losing MIME grouping.

## CLI proposal

Use one binary:

```sh
richclip <command>
```

### `list`

Human display by default, JSON for scripts.

```sh
richclip list
richclip list --json
richclip list --limit 50
richclip list --mime image/png
richclip list --query 'terminal rust error'
```

Example human output:

```text
01JZ...  2m ago   image/png, text/plain   screenshot of rust panic
01JY...  8m ago   text/html, text/plain   copied web fragment
```

JSON should be stable and script-friendly:

```json
{
  "id": "01JZ...",
  "created_at": "2026-06-03T12:34:56+10:00",
  "label": "screenshot of rust panic",
  "formats": [
    {"mime": "image/png", "size": 184221, "role": "offered"},
    {"mime": "text/plain", "size": 82, "role": "derived"}
  ]
}
```

### `update`

This is the main editing API.

```sh
richclip update <id> --set-mime text/plain=@label.txt
richclip update <id> --set-mime image/png=@new.png
richclip update <id> --remove-mime text/html
richclip update <id> --set-label 'screenshot of rust panic'
richclip update <id> --set-meta ocr=@ocr.json
richclip update <id> --no-offer application/x-richclip-label
richclip update <id> --offer text/plain
```

MIME update semantics:

```text
--set-mime MIME=@path
  add or replace that MIME blob

--set-mime MIME=-
  read blob from stdin

--remove-mime MIME
  remove that MIME from the item

--offer MIME / --no-offer MIME
  control whether that MIME is advertised when restoring

--role MIME=offered|derived|internal
  mark whether this is real clipboard data or generated support data
```

Important design choice: **labels should normally be metadata, not MIME types**. Only add `text/plain` or other MIME types when you actually want paste targets to see that generated representation.

### `delete`

Soft-delete by default, with hard-delete option.

```sh
richclip delete <id>
richclip delete <id> --mime text/html
richclip delete <id> --hard
richclip delete --older-than 30d
```

I would make MIME deletion available through both `delete` and `update`, but document `update --remove-mime` as the preferred form.

### `watch`

For an external labeller.

```sh
richclip watch
richclip watch --json
richclip watch --event item-added
richclip watch --event item-updated
richclip watch --mime image/png
```

Example event:

```json
{
  "event": "item-added",
  "id": "01JZ...",
  "created_at": "2026-06-03T12:34:56+10:00",
  "formats": ["image/png", "text/html", "text/plain"]
}
```

A labeller could do:

```sh
richclip watch --json --event item-added --mime image/png |
while read -r event; do
  id="$(jq -r .id <<<"$event")"
  richclip decode "$id" image/png > /tmp/clip.png
  label="$(label-image /tmp/clip.png)"
  richclip update "$id" --set-label "$label"
done
```

### Additional commands worth adding

Even if the basic API is `list`, `update`, `delete`, `watch`, I’d add these because they make the system usable:

```sh
richclip restore <id>
richclip decode <id> <mime>
richclip formats <id>
richclip inspect <id> --json
```

`restore` is the command that asks the daemon to become clipboard owner and advertise that item’s MIME types.

```sh
richclip restore <id>
richclip restore <id> --paste-once
richclip restore <id> --only text/plain
```

`decode` is the equivalent of `cliphist decode`, but MIME-aware:

```sh
richclip decode <id> image/png > image.png
richclip decode <id> text/html
```

## Daemon behavior

### Capture flow

```text
selection changes
  get data offer
  collect advertised MIME types
  filter MIME types
  receive each accepted MIME type
  store blobs
  create item row
  emit item-added event
```

Filtering matters. Some apps may advertise large, redundant, or awkward types. Start with a default allowlist:

```text
text/plain
text/html
text/uri-list
image/png
image/jpeg
image/webp
image/bmp
application/json
application/rtf
```

And a denylist / size limit:

```text
max item size
max single format size
deny application/octet-stream by default?
deny huge portal/file-transfer formats initially?
```

### Restore flow

```text
richclip restore <id>
  daemon loads item formats where offer_on_restore = true
  creates Wayland data source
  offers each MIME type
  sets source as current selection
  stays alive
  on send(mime, fd):
    streams blob bytes into fd
```

This lazy serving model is important: the compositor does not simply hold all clipboard bytes for you; the selection owner needs to provide the requested format when another client asks for it.

## Labelling model

A separate labeller should not mutate original bytes unless explicitly asked.

For an image item:

```text
image/png
  original captured bytes
  offer_on_restore = true
  role = offered

label
  metadata.label
  not offered to paste targets

ocr
  metadata.ocr
  maybe included in search_text

text/plain
  optional derived MIME
  offer_on_restore = false by default
```

So the labeller can enrich the item without changing paste behavior:

```sh
richclip update "$id" \
  --set-label "$label" \
  --set-meta image.label.model="$model" \
  --set-meta image.label.confidence="$confidence"
```

If you later want a picker mode where selecting an image pastes the generated label instead, that can be a restore option:

```sh
richclip restore "$id" --only text/plain
```

or a generated derived MIME:

```sh
richclip update "$id" --set-mime text/plain=- --role text/plain=derived --no-offer text/plain
```

## Picker integration

Keep the picker separate. The CLI should make fuzzel integration trivial:

```sh
id="$(
  richclip list --json |
  jq -r '.[] | "\(.id)\t\(.label // .search_text // "")\t\(.formats | map(.mime) | join(","))"' |
  fuzzel --dmenu |
  cut -f1
)"

[ -n "$id" ] && richclip restore "$id"
```

Later, a richer picker can show thumbnails from:

```text
$XDG_CACHE_HOME/richclip/thumbs/<item-id>.webp
```

But the core system should not depend on fuzzel, rofi, or a GUI.

```text

uuid/ulid   ids
serde       JSON events/API
tokio       daemon, IPC, labeller-friendly async
tracing     logs
```

Wayland side: use `wayland-client` plus generated protocol bindings for `wlr-data-control`; hide it behind your own small trait so you can later support `ext-data-control` without touching the DB/CLI.

```rust
trait ClipboardBackend {
    async fn run_capture_loop(&mut self, sink: CaptureSink) -> anyhow::Result<()>;
    async fn restore_item(&mut self, item: RestorableItem) -> anyhow::Result<()>;
}
```

## IPC API

The CLI should talk to the daemon for operations that affect live clipboard ownership or event streams.

```text
ListItems
GetItem
UpdateItem
DeleteItem
RestoreItem
WatchEvents
```

Use newline-delimited JSON initially. Easy to debug, fine for local IPC.

```json
{"cmd":"restore-item","id":"01JZ..."}
```

Daemon response:

```json
{"ok":true}
```

Watch stream:

```json
{"event":"item-added","id":"01JZ..."}
{"event":"item-updated","id":"01JZ...","changed":["label"]}
```

## Update semantics and concurrency

Use optimistic item revisions:

```sql
ALTER TABLE items ADD COLUMN revision INTEGER NOT NULL DEFAULT 0;
```

Every update increments `revision`.

```text
richclip update <id> --expect-revision 12 ...
```

This matters if a labeller updates an item while the user deletes or edits it. The CLI can default to no revision check, while internal labeller flows can be stricter.

## MVP phases

### Phase 1: storage + CLI

Implement:

```text
list
formats
decode
update
delete
```

Use manual import at first:

```sh
richclip update new --set-mime image/png=@foo.png
```

This validates DB/blob/update semantics without Wayland complexity.

### Phase 2: capture daemon

Implement:

```text
richclipd capture
richclip watch
```

Capture multi-MIME offers into grouped items.

### Phase 3: restore provider

Implement:

```text
richclip restore <id>
```

Advertise all stored MIME types and lazily serve requested blobs.

### Phase 4: labeller

Implement external process first:

```text
richclip watch -> label image -> richclip update
```

Keep labelling out of the daemon initially. The daemon should be clipboard plumbing, not model orchestration.

### Phase 5: picker polish

Add:

```text
thumbnail generation
ranking/search
fuzzel formatter
maybe a small TUI/GUI later
```

## Open design decisions

The main ones I’d settle early:

```text
Should generated text/plain be offered by default?
  I think no. Labels should be metadata unless explicitly promoted.

Should deleting an item delete blobs immediately?
  I think no. Soft-delete item, GC unreferenced blobs later.

Should duplicate clipboard selections create new history rows?
  Probably configurable:
    dedupe exact item_hash by default
    bump last_seen_at maybe
    optional keep duplicates

Should the daemon capture all MIME types?
  No. Use allowlist + size limits first.

Should primary selection be supported?
  Later. Keep CLIPBOARD first.
```

The resulting system is basically: **CopyQ’s item model, cliphist’s scriptability, and Wayland-native multi-MIME restore**, with a clean `watch → update` loop for async labelling.
